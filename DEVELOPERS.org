* Running

- "cargo run" will run "mcap"

- create test-data:
  - mkdir data/
  - cargo run -- publish kitten-catalog/ data/published

- tests (at least one test requires above test-data):
  - cargo test
  - cargo bench
  - cargo llvm-cov --html

- linting:
  - run these on any commit, "main" should always pass these
  - cargo fmt
  - cargo clippy

- prose documentation (includes a glossary of terms we typically capitalize like "Read Cap"):
  - cargo install mdbook mdbook-glossary
  - mdbook serve ./book/
  - sensible-browser http://localhost:3000

For memory use, there is a Nix flake for setup too.
  - nix run '.#memuse'
  - this should output something like:

        Max heap usage of 60087 bytes for encoding 311615 bytes
        Max heap used is 19 percent of the input file.

(On Debian, you can get the required Nix setup via "apt install
nix-setup-systemd" followed by adding your user to "nix-users")

* Overview

We assume you're genrally familiar with Rust development.
This repository tries to follow "normal Rust idioms" so if you spot something weird, please get in touch!

This is a "workspace" in Cargo + Rust terms, with two items:

- "magic_cap/": the Rust library
- "cli/": code that uses the above to make the "mcap" CLI tool

"cargo run" at the top level runs "mcap" the CLI tool.
So, it builds everything since mcap needs the library.
All code should have automated tests (coverage is not currently 100% so this is aspirational).

The README.org and this file use Emacs' "Org Mode", including some things to run the examples.
Not everyone uses Emacs, so you may extract and run such examples the same way CI does:

- emacs --script run-readme.el
- bash -e data/readme-examples.sh

We ourselves use "jujutsu" / "jj" for development, which automatically adds all files.
Thus, there is an ignored directory "data/" where examples tend to dump results (so they don't accidentally make it into the repository).
Everyone may contribute using Git directly (though you may use "jj" if you prefer).

The canonical example data is "kittens-catalog/" (used via "--catalog ./kittens-catalog" on the CLI).
We often also have "data/root" as an additional Catalog (see below, or the prose docs).

* Tools

**encode-kittens.py**: this creates the example Catalog using the demo kitten pictures.
This takes all the pictures in ``data/kittens`` and encodes them to the Catalog rooted at ``./kitten-catalog``.
NOTE that if you do this, all the Read Cap strings in the examples need to be changed!
There is no automation for this!

**decode_cap.py**: read and verify the metadata (and encrypted metadata) when given a Read Cap and a Data file.
For example:

#+begin_src sh :results output
python decode_cap.py kitten-catalog/88/884ef78b37fd33ac3fa8f8e939ed68e8d4b35710908fddd411f4d2314cba66af mcap0rwedkkhZUU4LIEBS9VypVCYO6YQrVpkYhazyNtg16Kzhqt4pKhRGjXNLLEhdYG-vZ
#+end_src

* Making a Release

- ensure on main (via "jj", perhaps a "jj new")
- update versions
  - magic_cap/Cargo.toml
  - mcap/Cargo.toml
  - ./Cargo.toml (dependency ... can we automate?)
- test
  - cargo publish --workspace --all-features --dry-run
- actually publish:
  - cargo login
  - cargo publish --workspace --all-features
